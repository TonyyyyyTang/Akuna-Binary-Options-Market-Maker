# 这次比赛，我是怎么一步步做下来的

我第一次接触二元期权做市，是从这个比赛开始的。0 或 1 的到期收益不难理解，真正让我困惑的是交易过程：机器人究竟和谁交易，RFQ 为什么不知道客户方向，FOK 为什么不能只接一部分，以及交易以后现金到底怎么变化。

一开始我甚至问过，每次运行测试是不是会影响下一次的 cash balance。这不是一个已经熟悉量化研究的人一上来就设计完整系统的故事。我是在写代码的同时补金融机制和 Python 基础。

## 先把小版本跑起来

最早的版本只报 bid=0、offer=1，数量是 1，基本不接 FOK。它通过了交易测试，但定价测试先因为返回 None 报错，再因为统一返回 0.5 而失败。

我后来才弄清楚，19/20 pass 并不代表机器人已经很强。有些测试只要求不出错、不破产，另外一些即使排名靠后也会给部分分数。真正需要观察的是每个场景的收益和排名。

接着我把定价拆开：先做 FED 的离散状态转移，再做两家公司的估值分布，最后做公司之间的比较合约。期间还弄懂了 `items` 和 `items()` 的区别、类型标注、下划线和辅助函数。能写完一部分就运行一次，比一下子面对一大段代码有效得多。

给定真实参数的定价测试最终和参考值对上了。这个阶段验证的是公式；从有限历史里估计参数，仍然是另一个问题。

## 最大的一次突破，其实是数量

我先花了不少时间调整 FOK，因为方向、价格、数量都已经给出，看起来更容易判断。但很多修改几乎没有效果，我开始怀疑是不是在一个小问题上反复钻。

后来发现，报价数量一直被限制在 1。价格即使更合理，也只争取到很少的成交。把没有最坏损失的边界报价数量提高到 10 后，一个开发测试的收益直接从 6 变成了 27。

再往后，主动报价的数量才开始真正跟本金、每张合约的最大损失和仓位容量联动。这让我学到，修改没效果时，需要检查数量、现金底线、仓位上限、价格取整和状态开关，而不只是继续改那个系数。

## 版本不是一开始就很整齐的

我试过库存偏移、滚动估计、对手方反馈、FOK 价格和方向信号，也试过拿不到 RFQ 成交时逐渐改变价差。有些修改没有可观察的作用；有些改善一个场景，同时损害另一个。

中间我确实出现过版本混乱。后来才开始保存完整的收益和分数序列，保留一个稳定版本，再用它比较新想法。最终的 V7B 加了高仓位才开启的保护，但在开发测试上和 V4I 的结果完全一样。这个保护是否帮助了最终隐藏评测，我没有证据。

## 18.5 分之后，最应该承认的事

最终版本在开发期间能看到的测试上是 18.5/20，16 个计分交易场景里 12 个满分，记录的运行中没有破产。但正式结果出来后，我没有进入前三十。

我在比赛后期已经担心过拟合：为什么某个条件只影响一个熟悉的测试？为什么按初始本金设置那么多分支？这些问题提得对，但没有及时配套一个独立验证环境。我还是反复用相同的测试结果判断改动好坏。

现在我能看到代码里具体的局限：小本金场景没有持续更新参数；model_ready 会被开局状态锁住；库存控制主要看单合约；有些地方把抵押金占用后的余额当作盈利缓冲。它们在观察过的场景上保住了分数，却没有经过足够广泛的验证。

我不知道最终评测中每个场景的结果，因此不能把排名全部归因于其中某一段代码。更确定的教训是，反复测试同一组市场，可以让我越来越熟悉那组市场，却不能自动证明换一组仍然有效。

## 比赛结束以后

我开始读其他参赛者的代码，也找到了社区 arena。下一步应先把评估过程补起来：改变历史长度、参数、流量和竞争者，提前保留不参与调参的场景；逐笔检查资金账本；再研究连续的不确定性估计和跨合约风险。

我没有在比赛中实现 RL。它是赛后看到别人分享才继续思考的方向。能不能学出好策略，还需要一个值得信任的环境来判断。

这整个过程有 ChatGPT 和 Codex 的帮助：解释概念、排查 Python 错误、生成候选代码和审查逻辑。我自己运行提交、追问假设、比较结果，也不断要求把实现拆成我能理解的步骤。把经历放出来，是为了留下这些真实的转变，而不是把它包装成从一开始就设计完美的项目。
